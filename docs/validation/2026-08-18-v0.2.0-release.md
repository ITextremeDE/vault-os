# Vault-OS 0.2.0 release validation

- Date: 2026-08-18
- Package: `0.2.0`
- Verdict: Passed
- Scope: automated acceptance, lifecycle upgrade, synchronized-device boundary,
  production MindOS verification, and fresh public-tag validation

## Automated acceptance

The complete documented acceptance suite passed:

- 62 unit and integration tests;
- portability validation for 151 distributable files and 19 manifests;
- portability-matrix validation for 119 classified source files;
- manifest validation for 25 core files, 111 files in 14 modules, 11 instance
  seeds, and one runtime artifact; and
- `git diff --check`.

GitHub Acceptance also passed for the release commit.

## Release upgrade

An isolated temporary vault was installed from package `0.2.0-dev.5` with all
14 optional modules. The `0.2.0` release candidate upgraded the installation,
verified 109 unchanged managed files, preserved all 11 instance files, updated
only device-local release metadata, and finished with a healthy `doctor --ai`
result.

## Synchronized-device boundary

The upgraded primary vault was transferred to a temporary secondary vault while
excluding the documented device-local `.vault-os/`, `.agents/`, `.claude/`,
`.codex/`, `.qmd/`, and `.mcp.json` paths. `device-sync` reconstructed the local
`0.2.0` release lock after verifying all 109 managed files and 11 instance
files. A checksum snapshot confirmed that no synchronized file changed.

Local `agent-init --provider codex` recreated provider discovery on the
secondary device, and `doctor --ai` reported the installation healthy.

## Production MindOS verification

The established MindOS instance on the primary macOS device and the synchronized
Linux server copy were both advanced through the canonical Vault-OS lifecycle to
`0.2.0`. Each installation reported zero pending managed changes and a healthy
`doctor --ai` result. MindOS content validation finished with zero errors and
zero warnings. Existing user-owned journal work remained outside the release
scope.

## Fresh public-tag verification

The public `v0.2.0` tag was cloned into a new temporary directory after
publication. Its manifest version and changelog heading matched the tag. The
complete acceptance suite passed again, and a clean vault installation with all
14 modules finished with a healthy `doctor` result.

The annotated `v0.2.0` tag resolves to the same release commit on GitHub and the
Forgejo mirror, and the GitHub release is published for that tag.

## Boundaries and skipped clients

- Codex provider discovery was exercised structurally and through
  `doctor --ai`; no interactive Codex session was required for this release.
- Claude Code was not exercised directly; its adapter remains covered by the
  automated structural and lifecycle tests.
- The isolated synchronized-device check simulated the documented file boundary;
  the already established production MindOS synchronization path supplied the
  real-world secondary-device evidence.
- No `.obsidian` directory or user-owned MindOS content was modified by the
  release lifecycle.
